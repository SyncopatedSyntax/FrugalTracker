> explain B2 more with an example. If a non-based currency is used for a transaction, I want the base currency amount locked in as of the time of the transaction, because currency exchange rate can fluctuate. And the base currency amount shouldn't change after the transaction is logged.

## 73. Retry GitHub backup on transient "Load failed" network blips

> Take a look at the backup error in the log: [debug log showing days of successful auto-backups, then a single 2026-07-18T15:19:25 failure — getFileSha OK (HTTP 200) then putFile "TypeError: Load failed" — with a manual retry ~18s later fully succeeding]

**Result:** diagnosed from the log the user pasted. Backups had run cleanly for days; one auto-backup failed with the GET succeeding and the very next PUT throwing `TypeError: Load failed` ~0.6s later (before any HTTP response), and an immediate manual retry succeeded. That's iOS Safari's signature for a `fetch()` cut off at the network layer before a response arrives — on iOS almost always the web view being suspended/backgrounded mid-request (this backup fires on app open, and iOS freezes PWAs the instant you switch away or lock the screen) or a momentary connectivity blip. Not a token/permission/repo problem — the recovery proves it. The real defect on our side: a single transient blip during the *unattended* auto-backup wrote `lastBackupStatus: 'error'`, surfacing a scary "failed" state on the backup screen even though the next run succeeds, because there was no retry.

**Fix:** added a `withRetry()` wrapper in `lib/githubBackup.ts` that retries an operation up to two extra times (400ms, 1200ms backoff) **only** on network-layer `TypeError`s — a real HTTP-status error (403/409/etc., thrown as a plain `Error`) is deliberately not retried, since that's a genuine problem the user should see. `putFile` and `getFileContent` (the backup-write and restore-read paths) now run inside it; `putFile` re-reads the file's sha on each attempt, so a retry after a lost-response PUT uses the current sha rather than a stale one that would 409. Each retry lands its own debug-log line, so the trail still shows the blip → retry → success sequence. `testConnection` is left as-is (user-initiated, they can just tap again). So the exact failure in the log would now self-heal on the first retry instead of marking the backup failed.

**Verified:** 4 new unit tests in `githubBackup.test.ts` (25 → 29 in that file) using fake timers: `putFile` retries a `TypeError` and succeeds; a 403 is not retried (single attempt); `backupNow` rides through a transient blip on the first PUT and records `success`; and exhausting all retries records `error` with the message. `npm run build` and `npx vitest run` (171 tests, +4) both clean — logic-only change, no UI surface, and the new tests drive the retry/backoff through `backupNow` end-to-end. Bumped to **v1.4.1**, committed, pushed.
